When ownership changes, explain the current code structure and behavior first, then document the gap between requested work and actual implementation.

## Prepare the sources

Prepare the repository and branch, or a versioned code snapshot, together with requirements notes and existing operations documents. Distinguish snapshot-based analysis from a review of the latest repository.

## Check structure and implementation scope

Ask in chat for a diagram of key components and dependencies. Separate verified implementation, requested work, and unknowns for each feature, with source files. Explain production access management using both role-checking code and operational policies.

## Help the next owner continue

Document run and test steps, known limitations, open decisions, and owners. Put unimplemented requests in an improvement document for the coding agent to read over MCP. After changes are pushed, check updates to existing documents and canvases linked to the repository and branch, then reconcile the handover materials.

## Example chat request

```text
Read this repository and the handover notes. Create a document and diagram explaining the current structure.
Separate completed features, implementation limits, requested work, and unknowns with source files.
Include run and test steps and questions for the next owner.
Keep suggested improvements separate from established feature descriptions.
```

<Note>Supply deployment, recovery, and operational owners from actual team records. For reproducible test records, include the commands actually run and results checked.</Note>
