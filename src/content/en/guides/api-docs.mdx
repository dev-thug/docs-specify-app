When API code changes faster than its explanations and examples, connect repository changes to proposed documentation updates.

## When this is your problem

A changed parameter or response field can leave old values in the docs and break integrations built from those docs. Updating only the API reference can leave the overview and operations guide describing different behavior.

## Solve it with Specify

1. Connect a repository with routes, handlers, and schemas to a document project.
2. Use an API documentation skill and the push trigger to prepare updates backed by code changes.
3. Compare requests, responses, errors, and examples with code, and check related documents before applying changes.

## What you get

Prepare API documentation updates with code-change evidence and before-and-after content. Review shared values across documents and compatibility impacts.

## Set up

<Steps>
  <Step title="Connect the repository with your API code">
    Connect the repository and branch containing your routes, handlers, and schema definitions as the source of a document project. If your schemas live in a separate repository, add another source.
  </Step>
  <Step title="Select an API reference document skill">
    Select a document skill that creates an API reference, and in the focus field, describe the target readers (internal team, external partners, and so on) and the scope to cover.
  </Step>
  <Step title="Turn on the push trigger">
    Turn on **Trigger on push** for the default branch to receive a proposed update every time an API change lands.
  </Step>
</Steps>

## What to check when reviewing proposed updates

| Area | What to check |
| --- | --- |
| **Requests** | Path, method, path and query parameters, request body schema, and required fields |
| **Responses** | Response fields for each status code, types, nullability, and pagination format |
| **Authentication** | Required authentication method, scopes, and where the token is sent |
| **Errors** | Error codes and messages, and whether the request can be retried |
| **Examples** | Whether request and response examples match the new schema |
| **Compatibility** | Whether the change breaks existing integrations, such as removing or renaming a field, and whether migration guidance is needed |

<Warning>
  An automatic edit may not be enough for changes that break existing integrations. Have a person decide whether a changelog entry and migration guidance are needed, and fill them in.
</Warning>

## Use with coding agents

Connect [Specify MCP](/en/mcp/overview) so Claude Code or Codex can reference your workspace's API docs directly while changing the API. You get to work on docs and code in the same context.

## Comparing every affected document

Do not finish review after updating only the API reference. If the same default limit, retention policy, or status code appears in an overview or operational document, compare all of them with the current code and tests.

After deletion or renaming, check examples, source links, and document titles too. Even when a test line number exists, read the line to confirm it actually verifies the documented status code or behavior. See [Review and apply proposed updates](/en/guides/review-proposals) for review criteria.
