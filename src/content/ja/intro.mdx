Specifyはコード変更を読み取り、更新すべき開発ドキュメントを見つけて、レビューできる修正案につなげます。ドキュメントを書く余裕のないチームでも、GitHubリポジトリを接続するだけで、コードとともに更新される開発ドキュメントを維持できます。

Specifyの活用方法は大きく2つあり、チームの状況に応じて組み合わせて使えます。

|  | ドキュメント自動化 | Specify MCP |
| --- | --- | --- |
| **概要** | GitHubリポジトリを根拠に開発ドキュメントを生成し、コード変更に合わせて修正案を用意するワークスペース機能 | Claude Code・Codex・Cursorなどのコーディングエージェントが、チームのワークスペースのドキュメントと文脈を読めるようにつなぐMCPサーバー |
| **適した用途** | API・アーキテクチャ・オンボーディングのドキュメントをコードと同期 | プロジェクトの背景を毎回エージェントに貼り付けることなく、チームの文脈の上で作業 |
| **はじめる** | [クイックスタート](/ja/quickstart) | [MCPの概要](/ja/mcp/overview) |

## Specifyができること

<CardGroup cols={3}>
  <Card icon="git" title="コードとドキュメントをつなぐ">GitHubリポジトリとブランチをドキュメントプロジェクトに接続し、コードを根拠に最初のドキュメントを生成します。</Card>
  <Card icon="pr" title="根拠のある修正案">コードが変わると影響を受けるドキュメントを見つけ、変更理由と修正前後を含む修正案を用意します。</Card>
  <Card icon="message" title="チームの文脈で回答">ドキュメント・意思決定・コードの記録を根拠に、「なぜこう作ったのか」「どこにあるのか」に答えます。</Card>
</CardGroup>

<Note>
  新しいドキュメントプロジェクトは自動反映なしで始まります。すべての変更はまず根拠とともに修正案として届き、その後の反映方法はプロジェクト設定と適用ポリシーに従います。
</Note>

## 正確なドキュメントを支える根拠

SpecifyのAIは、一般的な知識だけでドキュメントを作り上げることはありません。書く前に根拠を検索します。

<CardGroup cols={3}>
  <Card icon="search" title="ワークスペースRAG" href="/ja/knowledge/rag">ワークスペースのドキュメント、アップロードしたファイル、接続された資料を検索し、自分たちのチームの事実を根拠に回答・作成します。</Card>
  <Card icon="library" title="規格文書ライブラリ" href="/ja/knowledge/standards">IEC 62304・ISO 14971などの規格の条項を検索して引用し、根拠のない内容には印を付けます。</Card>
  <Card icon="sparkles" title="作業に合ったモデル" href="/ja/models/choosing">検索・要約には軽量なモデルを、ドキュメント作成にはドキュメント作業に強いモデルを選びます。</Card>
</CardGroup>

## 主な活用例

- **API・開発ドキュメントの更新** — APIコードがあるリポジトリを接続しておくと、エンドポイント・リクエストスキーマ・レスポンスフィールドがコードとずれるたびに修正案が用意されます。確認項目は[APIドキュメントを最新に保つ](/ja/guides/api-docs)を参照してください。
- **開発者のオンボーディング文書** — リポジトリの構成と実行方法を根拠に、新しいメンバーが初日にローカル実行までたどり着く文書ドラフトを作成します。コードにないチームの手順は人が補完します。[オンボーディングドキュメントの生成](/ja/guides/onboarding-docs)を参照してください。
- **チームのナレッジ検索** — 文書を探し回ったり同僚を呼び止めたりせずに、ワークスペースの文書と資料を根拠に答えを得られます。[AIに質問する](/ja/guides/ask-ai)を参照してください。

セキュリティ質問票への回答、プロジェクトの引き継ぎ、顧客向け案内など、開発以外の業務の例も[活用例一覧](/ja/guides/use-cases)で、用意する資料と成果物を例ごとに確認できます。
