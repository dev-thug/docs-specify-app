Specifyはコード変更を読み取り、更新すべき開発ドキュメントを見つけて、レビューできる修正案につなげます。ドキュメントを書く余裕のない小さなチームでも、GitHubリポジトリを接続するだけで、コードとともに更新される開発ドキュメントを維持できます。

Specifyの活用方法は大きく2つあり、チームの状況に応じて組み合わせて使えます。

|  | ドキュメント自動化 | Specify MCP |
| --- | --- | --- |
| **概要** | GitHubリポジトリを根拠に開発ドキュメントを生成し、コード変更に合わせて修正案を用意するワークスペース機能 | Claude Code・Codex・Cursorなどのコーディングエージェントが、チームのワークスペースのドキュメントと文脈を読めるようにつなぐMCPサーバー |
| **適した用途** | API・アーキテクチャ・オンボーディングのドキュメントをコードと同期 | プロジェクトの背景を毎回エージェントに貼り付けることなく、チームの文脈の上で作業 |
| **はじめる** | [クイックスタート](/ja/quickstart) | [MCPの概要](/ja/mcp/overview) |

## Specifyができること

<CardGroup cols={3}>
  <Card icon="git" title="コードとドキュメントをつなぐ">GitHubリポジトリとブランチをドキュメントプロジェクトに接続し、コードを根拠に最初のドキュメントを生成します。</Card>
  <Card icon="pr" title="根拠のある修正案">コードが変わると影響を受けるドキュメントを見つけ、変更理由と修正前後を含む修正案を用意します。</Card>
  <Card icon="message" title="チームの文脈で回答">ドキュメント・意思決定・コードの記録を根拠に、「なぜこう作ったのか」「どこにあるのか」に答えます。</Card>
</CardGroup>

<Note>
  新しいドキュメントプロジェクトは自動反映なしで始まります。すべての変更はまず根拠とともに修正案として届き、その後の反映方法はプロジェクト設定と適用ポリシーに従います。
</Note>

## 主な活用例

- **API・開発ドキュメント** — エンドポイント、リクエストスキーマ、レスポンスフィールドがコードとずれないように維持します。[APIドキュメントを最新に保つ](/ja/guides/api-docs)を参照してください。
- **オンボーディングドキュメント** — リポジトリの構成と実行方法を根拠に、新しいチームメンバーが初日に実行までたどり着けるドキュメントを作成します。[オンボーディングドキュメントの生成](/ja/guides/onboarding-docs)を参照してください。
- **チームのナレッジ検索** — ドキュメントを探し回ったり同僚を呼び止めたりせずに、チームの文脈を根拠に答えを得られます。[AIに質問する](/ja/guides/ask-ai)を参照してください。
