APIコードの変更に説明や例が追いつかない場合、リポジトリの変更を文書修正案につなげてレビューします。

## こんな問題があるとき

パラメーターや応答フィールドが変わっても文書に古い値が残ると、それを使う連携でエラーが起きます。レファレンスだけを修正すると、概要や運用ガイドが異なる動作を説明することがあります。

## Specifyで解決する

1. ルート・ハンドラー・スキーマがあるリポジトリを文書プロジェクトに接続します。
2. API文書スキルとpushトリガーで、コード変更を根拠のある修正案につなげます。
3. リクエスト・レスポンス・エラー・例をコードと照合し、関連文書も確認してから反映します。

## 得られる成果

コード変更の根拠と修正前後を確認できるAPI文書の修正案を準備します。関連文書の値と互換性への影響もレビューします。

## 設定する

<Steps>
  <Step title="APIのコードがあるリポジトリを接続する">
    ルート、ハンドラー、スキーマ定義があるリポジトリとブランチを、ドキュメントプロジェクトのソースとして接続します。スキーマが別のリポジトリにある場合は、ソースをもう1つ追加します。
  </Step>
  <Step title="APIリファレンスのドキュメントスキルを選択する">
    APIリファレンスを作成するドキュメントスキルを選択し、重視する点に対象読者（社内チーム、外部パートナーなど）と扱う範囲を書きます。
  </Step>
  <Step title="pushトリガーをオンにする">
    デフォルトブランチで**push で実行**をオンにして、APIの変更が反映されるたびに修正案を受け取ります。
  </Step>
</Steps>

## 修正案をレビューするときに確認すること

| 領域 | 確認すること |
| --- | --- |
| **リクエスト** | パス、メソッド、パス・クエリパラメーター、リクエストボディのスキーマと必須かどうか |
| **レスポンス** | ステータスコードごとのレスポンスフィールド、型、nullableかどうか、ページネーションの形式 |
| **認証** | 必要な認証方式、権限スコープ、トークンを渡す場所 |
| **エラー** | エラーコードとメッセージ、再試行できるかどうか |
| **例** | リクエスト・レスポンスの例が新しいスキーマと一致しているか |
| **互換性** | フィールドの削除や名前の変更など、既存の連携を壊す変更かどうか、移行ガイドが必要かどうか |

<Warning>
  既存の連携を壊す変更は、自動修正だけでは不十分な場合があります。変更履歴や移行ガイドが必要かどうかを人が判断し、補ってください。
</Warning>

## コーディングエージェントと一緒に使う

[Specify MCP](/ja/mcp/overview)を接続すると、Claude CodeやCodexがAPIを修正している間に、ワークスペースのAPIドキュメントを直接参照できます。ドキュメントとコードを同じ文脈で扱えるようになります。

## 関連ドキュメント全体を照合する

APIレファレンスだけを修正してレビューを終えないでください。同じ既定limit、保持ポリシー、ステータスコードが概要や運用ドキュメントにもあれば、すべてを現行コード・テストと照合します。

削除・名前変更後は、例、ソースのリンク、ドキュメント名まで確認してください。テストの行番号が存在していても、その行が記載されたステータスコードや動作を実際に検証しているか読んでください。基準は[修正案のレビューと反映](/ja/guides/review-proposals)を参照してください。
