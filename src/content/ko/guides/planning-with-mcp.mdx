회의 후 기획이 바뀌는데 개발자는 이전 문서로 구현하고 있다면, Specify의 같은 기획 문서를 MCP로 읽어 현재 요구사항을 맞추세요.

## 이런 문제가 있다면

기획은 회의와 대화에서 바뀌고, 개발자는 앞서 받은 사본이나 에이전트 대화에 남은 내용을 기준으로 작업합니다. 취소 조건 하나를 바꿔도 화면·API·테스트에 어디까지 반영됐는지 서로 확인해야 합니다.

## Specify로 해결하기

1. 기획자가 Specify 에디터에서 현재 조건, 변경 이유, 수락 조건을 같은 문서에 정리합니다.
2. 개발자가 Claude Code·Codex에 MCP로 원문을 읽게 하고, 현재 코드와의 차이 및 구현 계획을 확인합니다.
3. 기획 변경 후 같은 본문을 다시 읽어 영향 범위를 맞추고, 개발 검토 문서에 구현 결과와 남은 질문을 돌려줍니다.

## 얻는 결과

기획과 구현의 차이, 변경된 수락 조건별 작업·테스트 목록, 남은 질문을 같은 팀 맥락에서 정리합니다. 기획자는 Specify에서, 개발자는 익숙한 코드 에디터에서 협업을 이어갑니다.

## 기획과 개발이 같은 문서를 보는 흐름

예를 들어 예약 서비스를 개발한다고 가정해 보세요. 기획자가 “예약 취소” 문서에 화면 흐름, 취소 조건, 예외와 수락 조건을 적습니다. 개발자는 코딩 에이전트에 이 문서를 읽게 한 뒤 현재 코드와 대조합니다. 기획이 바뀌면 파일을 다시 전달하는 대신, 같은 문서를 다시 읽어 변경된 요구사항을 반영합니다.

| 역할 | 사용하는 곳 | 남기는 결과 |
| --- | --- | --- |
| **기획자·PM** | Specify 에디터 | 현재 기획, 확정된 결정, 미정 질문, 수락 조건 |
| **개발자** | Claude Code·Codex와 코드 에디터 | 기획과 코드의 차이, 구현 계획, 코드와 테스트 |
| **팀** | Specify의 같은 문서와 별도 검토 문서 | 변경 이유, 개발 확인 사항, 구현 결과와 남은 질문 |

## 시작하기 전에

- 기획자와 개발자가 같은 워크스페이스의 대상 문서에 접근할 수 있어야 합니다.
- 개발자는 [에디터·에이전트 연결](/ko/mcp/connect)에 따라 Specify MCP를 Claude Code 또는 Codex에 연결합니다.
- 기획을 참고하는 작업은 읽기 권한으로 시작합니다. 구현 결과를 Specify 문서로 남기려면 [쓰기 권한](/ko/mcp/access)도 필요합니다.

## 기획을 구현으로 이어가기

1. **기획자가 문서를 정리합니다.** 목적, 화면 흐름, 확정 조건, 예외, 수락 조건을 구분합니다. 아직 결정하지 않은 항목은 질문으로 남깁니다.
2. **개발자가 MCP로 기획 원문을 읽습니다.** `search`나 `browse`로 문서를 찾고 `read_document`로 본문을 읽습니다. 문서 이름을 정확히 알려 주면 찾기 쉽습니다.
3. **에이전트가 기획과 코드를 대조합니다.** 이미 구현된 항목, 고쳐야 할 항목, 담당자에게 물을 항목을 나눠 구현 계획을 준비합니다.
4. **기획자가 협의 결과를 같은 문서에 반영합니다.** 바뀐 조건과 이유를 적고, 현재 조건과 이전 조건을 구분합니다.
5. **개발자가 변경된 문서를 다시 읽습니다.** 이전에 읽은 내용과 대조해 코드와 테스트의 영향 범위를 확인한 뒤 구현을 이어갑니다.
6. **개발 확인 사항을 문서로 돌려줍니다.** 쓰기 권한이 있으면 `create_document`로 별도 검토 문서를 만들거나, 합의한 섹션만 `update_document`로 갱신합니다. 기획자는 이를 보고 남은 결정을 정리합니다.

## 변경된 기획을 다시 읽는 예시

다음은 예약 서비스의 기획 예시입니다.

| 항목 | 처음 기획 | 협의 후 기획 |
| --- | --- | --- |
| **취소 가능 시점** | 예약 24시간 전까지 | 예약 12시간 전까지 |
| **취소 불가 화면** | 취소 버튼을 숨김 | 비활성 버튼과 사유를 표시 |
| **수락 조건** | 취소 가능 여부 검사 | 시간 경계와 비활성 안내도 검사 |

개발자는 조건을 코드에 복사해 둔 채 작업을 계속하기보다, 변경 후 같은 문서를 다시 읽게 합니다. 에이전트는 API 조건뿐 아니라 화면 상태와 테스트도 함께 수정할 대상으로 정리할 수 있습니다.

<Note>
  Specify 에디터는 팀의 실시간 공동 편집을 지원합니다. 코딩 에이전트는 MCP를 호출해 서버에 반영된 문서를 읽습니다. 기획 변경이 진행 중인 에이전트 대화에 자동으로 전달되는 방식은 아니므로, 변경 후에는 같은 문서의 본문을 다시 읽도록 요청하세요. 검색 색인 반영을 기다리는 대신 문서 ID를 알고 있다면 `read_document`로 직접 읽을 수 있습니다.
</Note>

## 복사해서 쓸 요청

**처음 구현 계획을 잡을 때**

> Specify MCP로 “예약 취소 기획” 문서를 찾아 본문을 읽어 줘. 확정된 요구사항과 미정 질문을 구분하고, 현재 코드와 대조해 구현 계획과 수락 조건별 테스트 목록을 정리해 줘. 문서에 없는 정책은 추측하지 말고 질문으로 남겨 줘.

**기획이 바뀐 뒤**

> 같은 기획 문서를 MCP로 다시 읽어 줘. 앞서 확인한 내용과 비교해 달라진 조건을 정리하고, 구현 중인 코드와 테스트에 영향을 주는 부분을 알려 줘. 이미 구현한 부분에서 바뀌어야 할 동작도 함께 확인해 줘.

**개발 결과를 공유할 때**

> Specify에 별도의 개발 검토 문서를 만들어 줘. 참고한 기획 문서, 반영한 요구사항, 확인한 테스트, 아직 결정이 필요한 질문을 정리해 줘. 확정 기획의 본문은 바꾸지 말아 줘.

## 협업할 때 확인할 것

- **확정 사항과 제안을 구분합니다.** 개발자의 제안은 기획자가 결정하기 전까지 별도로 남깁니다.
- **문서 이름과 ID를 유지합니다.** 같은 문서를 계속 다시 읽으면 중복 사본을 기준으로 구현하는 일을 줄일 수 있습니다.
- **중요한 변경 직전에 다시 읽습니다.** 구현 시작, 기획 변경 후, 최종 리뷰 전에 현재 본문을 확인합니다.
- **문서와 구현을 함께 검토합니다.** 화면, API, 예외, 테스트가 같은 수락 조건을 따르는지 확인합니다.

사용 가능한 도구와 입력값은 [MCP 제공 도구](/ko/mcp/tools)를 참고하세요.
